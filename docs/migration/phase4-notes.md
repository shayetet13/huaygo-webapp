# Phase 4 — Per-shop LINE OA + encrypted credentials: notes & deviations

**สถานะ: ✅ เสร็จสมบูรณ์และ verify แล้วทั้ง SQLite + Postgres (2026-07-11)**

## สิ่งที่ทำ

- **`lib/crypto.ts`**: AES-256-GCM envelope encryption (`encryptSecret`/`decryptSecret`) คีย์เดียวจาก `SHOP_SECRET_KEY` env (32-byte hex) เก็บ `shop_line_channels.channel_secret_enc`/`access_token_enc`
- **`lineClient.service.ts` รื้อใหม่ทั้งไฟล์**: ambient shop context ผ่าน `AsyncLocalStorage` (`runWithShopContext`) — `getMessageContent`/`getProfile`/`replyMessage`/`pushMessage` **ไม่เปลี่ยน signature** อ่าน `shopId` จาก context เอง resolve+decrypt credentials ต่อร้าน cache 5 นาที (`invalidateLineCredentialsCache`) มีแค่ `verifySignature(shopId, ...)` ที่รับ `shopId` ตรงๆ เพราะเป็น entry gate ก่อน context จะถูกสร้าง
- **`line.routes.ts`**: `POST /api/line/webhook/:shopSlug` resolve ร้านจาก slug (+ `status='active'`) → verify signature ด้วย secret ของร้านนั้น → ACK ทันที → ประมวลผล event ทั้งหมดใน `runWithShopContext(shopId, ...)`; `POST /api/line/webhook` (ไม่มี slug) เก็บไว้เป็น alias ชั่วคราวสำหรับร้าน 1 ระหว่างย้าย webhook URL เดิมที่ตั้งค้างไว้กับ LINE; ไฟล์ที่อัปโหลดย้ายจาก `data/line-uploads/*.jpg` → `data/line-uploads/<shopId>/*.jpg`
- **DB scoping ของ conversation state**: `line_conversation_state` PK คือ `(shop_id, line_user_id)` มาตั้งแต่ Phase 3 แต่โค้ดยังไม่ใช้จริง — Phase 4 นี้เพิ่ม `shopId` เป็นพารามิเตอร์แรกของ `getState/setState/resetState` และทุกฟังก์ชันที่เรียกต่อ (`recordNavigation, withStuckNudge, recordAndNudge, restart, goBack, handlePostback, handleDeleteSlip`) ใน `lineFlow.service.ts` — ตัดสินใจใช้ **explicit param ไม่ใช่ ambient context** สำหรับชั้น DB-scoping ทั้งหมด (ต่างจากชั้น LINE-API-credential ที่ใช้ ambient) เพราะฟังก์ชันเหล่านี้บางตัวถูกเรียกจาก route ของแอดมิน (ไม่มี webhook context ให้ดึง) ด้วย — คงหลักการเดียวกับ cross-tenant isolation test ของ Phase 3 ที่ต้องการ shop scoping แบบตรวจสอบได้ ไม่พึ่ง implicit state
- **`lineSubmission.service.ts`**: `createOrAppendSubmission` รับ `shopId` (ก่อนหน้านี้ INSERT ไม่เคยเซ็ต `shop_id` เลยตั้งแต่ Phase 3 — ทุก LINE submission ใหม่มี `shop_id = NULL` มาตลอด) · `resolveAppendTarget` scope ด้วย `shop_id` · `softDeleteSubmission` เพิ่ม `opts.shopId` ให้ทั้ง flow ลูกค้า (ผ่าน `handleDeleteSlip`) และแอดมิน (`lineReview.routes.ts`) ใช้ scope ได้
- **`paymentOrder.service.ts`**: `clearAwaitingPaymentIfMatches`/`startPaymentFlow` ปรับให้ส่ง `shopId` (จาก `line_submissions.shop_id` ที่มีอยู่แล้วในแถว) เข้า `getState`/`setState` ตาม signature ใหม่
- **`lineReview.routes.ts`**: เพิ่ม `requireShop` เต็มรูปแบบ — ทุก endpoint (list/days/search/detail/image/approve/reject/delete/payment-slip-image/record-payment/confirm-payment/cancel-payment) กรอง `shop_id = req.shop.id`; สลับจาก `getLastResetAtAnyShop()` → `getLastResetAt(shopId)` (มีอยู่แล้วตั้งแต่ Phase 3 แต่ยังไม่เคยถูกใช้เพราะรอ `requireShop`); ทุกจุดที่ `pushMessage` ห่อด้วย `runWithShopContext(shopId, ...)`
- **`paymentTimeout.service.ts` / `resultSync.service.ts`**: background poller ทั้งสองตัววิ่งข้ามทุกร้าน (ไม่ scope) — เพิ่ม `shop_id` เข้า query แล้วห่อ `pushMessage` แต่ละแถวด้วย `runWithShopContext(row.shop_id, ...)`; `LineResultNotification` เพิ่มฟิลด์ `shopId`, group ผลแจ้งเตือนด้วย `(shopId, lineUserId)` composite key แทน `lineUserId` เดี่ยวๆ
- **`shopLineChannel.routes.ts` (ใหม่)**: `GET/PUT /api/admin/shop/line-channel` (บันทึก channel id/secret/token เข้ารหัสก่อนเก็บ, ไม่เคยคืน secret/token ดิบกลับ) + `POST .../verify` (เรียก LINE `GET /v2/bot/info` จริงด้วย token ที่บันทึกไว้ ยืนยันว่าใช้ได้ + คืน webhook URL ให้แอดมินเอาไปตั้งในหน้า LINE Developers Console)
- **`db/seed.ts`**: `migrateLegacyLineCredentials()` — ครั้งเดียว เข้ารหัส `LINE_CHANNEL_SECRET`/`LINE_CHANNEL_ACCESS_TOKEN` (env เดิม) ใส่ `shop_line_channels` ให้ร้าน 1 ถ้ายังไม่มีแถว (idempotent, ไม่ทับค่าที่แอดมินตั้งใหม่ผ่านหน้า settings ไปแล้ว); `migrateLineUploadsToShopDir()` — ย้ายไฟล์รูปเก่าที่นอนแบนอยู่ที่ root ของ `data/line-uploads/` เข้า `.../1/` ครั้งเดียว
- **`config.ts`**: `lineChannelSecret`/`lineChannelAccessToken` เปลี่ยนชื่อเป็น `legacyLineChannelSecret`/`legacyLineChannelAccessToken` (optional แล้ว ใช้แค่ตอน migrate ครั้งเดียว) เพิ่ม `shopSecretKey` (required)

## บั๊กที่เจอระหว่างทำ (แก้แล้ว)

1. **`postgresClient.ts` ไม่รู้ว่า `shop_line_channels` ไม่มีคอลัมน์ `id`** — PK ของตารางนี้คือ `shop_id` ตรงๆ (ตั้งใจตั้งแต่ Phase 3 ตอนสร้างตารางไว้ล่วงหน้า) แต่ auto-`RETURNING id` logic ใน `postgresClient.exec()` ไม่มีตารางนี้อยู่ใน `NO_ID_TABLES` set ทำให้ `INSERT INTO shop_line_channels` (ทั้งจาก `migrateLegacyLineCredentials()` และ `PUT /api/admin/shop/line-channel`) พังกลางบูตด้วย `column "id" does not exist` บน Postgres จริง (SQLite ไม่เจอเพราะไม่มี auto-RETURNING logic แบบนี้) — เจอตอน live-boot ต่อ Supabase จริง ไม่ใช่จาก unit test เลย (สมกับ pattern ที่ Phase 2/3 เจอมาก่อน) แก้โดยเพิ่ม `'shop_line_channels'` เข้า `NO_ID_TABLES`

## ⚠️ เบี่ยงจากแผน / ตั้งใจเลื่อน

- **`orderLookup.service.ts` (`lookupOrderByRef`, `getOrderSummary`) ยังไม่ scope ด้วย `shop_id` ตรงๆ** — พึ่งพาข้อเท็จจริงที่ LINE ออก `userId` แยกต่อ channel/OA เสมอ (คนละร้าน = คนละ LINE OA = `userId` ไม่มีทางชนกัน) จึง isolate โดยธรรมชาติอยู่แล้วแม้ query จะกรองแค่ `line_user_id` — ต่างจาก `line_conversation_state`/`line_submissions` ที่ schema บังคับ composite key/คอลัมน์ `shop_id` ให้ query ต้องส่งมาด้วยอยู่ดี เก็บเป็นงาน hardening เพิ่มเติมได้ในอนาคตถ้าต้องการ defense-in-depth แต่ไม่ใช่ช่องโหว่จริงตอนนี้
- **Test suite เขย่าไฟล์จริงใน `data/line-uploads/`** — `shopIsolation.test.ts` import `db/seed.ts` ตรงๆ ซึ่งตอนนี้เรียก `migrateLineUploadsToShopDir()` ที่อ้าง path จริงแบบ hardcode (ไม่ผ่าน `DB_PATH` override เหมือน DB) รันเทสต์ครั้งแรกหลัง Phase 4 landing ย้ายไฟล์อัปโหลดจริง 4 ไฟล์เข้า `data/line-uploads/1/` ไปแล้ว (ผลลัพธ์ถูกต้องตามที่ Phase 4 ต้องการอยู่แล้ว แต่โดยหลักการเทสต์ไม่ควรแตะ filesystem จริงนอก sandbox ของตัวเอง) — ทำ idempotent แล้ว (รันซ้ำไม่มีไฟล์หลงเหลือให้ย้ายอีก) ไม่บล็อกอะไร แต่ flag ไว้เป็น test-hygiene debt

## Verify แล้ว

- Typecheck (`npx tsc --noEmit`) ผ่าน, ไม่มี error
- Vitest 98/98 ผ่านทั้งหมด (รวม `crypto.test.ts` 5 เคสจาก session ก่อน + `shopIsolation.test.ts` เดิม 6 เคส)
- **SQLite live boot**: server บูตสำเร็จ, migrate legacy LINE creds ของร้าน 1 อัตโนมัติ (channel secret/token จาก `.env` เดิม เข้ารหัสเก็บ DB ถูกต้อง) · `POST /webhook/no-such-shop` → 404 · `POST /webhook/shop-1` ด้วย signature ปลอม → 401 · ด้วย signature จริง (คำนวณจาก channel secret จริง) → 200 · `POST /webhook` (legacy alias) → 200 เหมือนกัน · ยิง `follow` event จริง → `line_conversation_state` ถูกสร้างด้วย `shop_id=1` ถูกต้อง + `replyMessage` เรียก LINE API จริงด้วย token ที่ decrypt จาก DB (ได้ `Invalid reply token` ตามคาด เพราะ replyToken เป็นของปลอม — พิสูจน์ว่า credential resolution ทำงานจริง ไม่ใช่แค่ไม่ throw) · `GET /api/admin/shop/line-channel` และ `POST .../verify` คืนข้อมูล bot จริง (`displayName: "KEYPOY"`) · `GET /api/admin/line-submissions` scope ตามร้านถูกต้อง
- **Postgres จริง (Supabase) live boot**: เจอบั๊ก `NO_ID_TABLES` ระหว่างนี้พอดี (ดูด้านบน) แก้แล้ว boot ผ่าน สร้าง schema/migration ครบ, smoke test ชุดเดียวกับ SQLite ทั้งหมดผ่านทุกข้อ (webhook 404/401/200×2, follow event, admin line-channel routes, admin review routes) ด้วยผลลัพธ์เดียวกัน (bot `KEYPOY` เหมือนกันเพราะ credentials จริงชุดเดียวกัน)
- ลบข้อมูลทดสอบ (`line_conversation_state` ของ LINE user ปลอม `Utestuser12345`/`UpgTestUser99999`) ออกจากทั้ง SQLite และ Supabase แล้ว, `.env` คืนกลับ `DATABASE_URL` เป็นคอมเมนต์ (SQLite mode พัก) ตามปกติ
